# Interface languages

Pi Pocket draws its interface in English. It can draw it in other languages too: the page is translated after it is
rendered, from a table of strings.

## Choosing a language

Appearance → Language. `English` and `中文` are there. A browser whose language starts with `zh` starts in Chinese; the
choice is kept in `localStorage` (`pocket.lang`) for that browser, so two people on one server can read it in two
languages.

## Adding a language

A language is one table plus one line in `web/i18n.js`.

1. `web/i18n.zh.js` is the model: `text` maps the English text exactly as the app renders it, and `patterns` maps text
   with a number or a name in it (`$1` is the first group).
2. Copy it to `web/i18n.<code>.js`, translate the values, keep the keys as they are.
3. In `web/i18n.js`, add the table to `tables` (`{ text, patterns, html }`, where `html` is the `<html lang>` value) and
   add `{ id, label }` to `LANGS` so it appears in Appearance.

Keys are the English text, not invented ids: a string the table does not have stays English, so a half-finished
translation is usable, and a new English string never breaks a page.

## What is not translated

- what someone typed, the model's answers, tool output, diffs, file contents and code: the translator skips those
  containers (`SKIP_TEXT` in `web/i18n.js`);
- theme names, model names, session titles and file paths;
- the server's own messages (`src/server/`), which are English for now.

## How it works

`web/i18n.js` runs at start: it translates the page, then watches the DOM. Every node Preact adds, and every later change
to a text node or to a `placeholder` / `title` / `aria-label`, is checked against the table. A microtask does the work,
not an animation frame, so a background tab and a phone that screen-locks still find the page translated when they come
back. Because matching is exact text, a translation cannot leak into a message: nothing else is rewritten.

A string that changes with a click (a menu item that becomes "Folded") is translated when it is drawn again, like any
other text.

## Limits worth knowing

- The launcher's search runs over the English strings, and the translation happens after the page is drawn: typing a
  Chinese word in the launcher finds nothing ("没有匹配"). Fixing that means translating the search index too, not just
  the page.

- A translated string has to be a whole text node. Text split by markup (`the <b>name</b> here`) is not matched, and
  stays English until the code that draws it passes a single string.
- The English keys come from the rendered page, so a string that only appears in a rare sheet is not in the table yet.
  Open the sheet, read the text, add the key.
- The translation is a runtime step, so there is a frame where English is visible before it is swapped. On a slow phone
  this is visible; drawing from the table at the call site (`t("Sessions")`) would avoid it, at the cost of touching
  every component.
